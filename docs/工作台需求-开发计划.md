## 0. 维护约定

- 任务以 `- [ ]` / `- [x]` 勾选；大项完成后在「里程碑状态」表打勾并填完成日期。
- 阻塞项在任务下用 `> 阻塞：` 记录原因与跟进人。
- 若范围变更：改 PRD → 改详细设计 → **再改本计划**，避免三份文档漂移。
- 建议每个里程碑结束时补一行 **Retrospective**（3 条以内：做得好的 / 需改进 / 下阶段注意）。

## 4. M1 — 信息架构与导航（无后端大改）

**目标**：用户心智上区分「工作台」与「平台管理」；现有能力可继续走原 API。

### 4.1 任务清单

- [x] **路由结构**：新增 `web-ui` 路由前缀，例如 `/workbench`（首页可为 Dashboard 或重定向到 Runs）。
- [x] **管理端归组**：将 `tenants`、`organizations`、`teams`、`members`、`audit-logs`、`tool-policies` 等归入侧边栏分组「平台管理」或 `/admin` 前缀（二选一，与详细设计 §7 一致）。
- [x] **工作台分组**：`workflows` 页面迁入 `workbench/runs` 或保留路径但导航显示为「工作台 · 流程与任务」。
- [x] **Layout**：`Layout.tsx` 更新导航项顺序与分组；可选为 workbench 使用略简化的顶栏（仍共用 scope）。
- [x] **Scope 提示**：未选 `team_id` 时，工作台核心操作（起流程）给出明确提示，引导选择 scope（沿用 `ADMIN_SCOPE_CHANGED_EVENT`）。
- [x] **文案**：页面标题、面包屑与按钮与 PRD 用语对齐（少提「工作流」技术词，多提「流程」「任务」）。
- [ ] **回归**：手动走通：选 scope → 打开原 Workflows 等价页 → 起模板 → 看板仍可用。（构建已通过；需在联调环境手测）

### 4.2 交付物

- 可合并的 PR：仅 `web-ui` + 必要静态资源；`App.tsx` 路由表更新。
- 截图或简短录屏（可选）：导航前后对比，附在 PR 描述。

### 4.3 验收（对齐 PRD §8 M1）

- 业务用户从主导航可进入工作台且不易误入租户/成员等管理页（除非权限设计允许同入口）。

## 5. M2 — 工作流模板出库表 + Resolver + start 兼容

**目标**：模板可配置；`POST /api/workflows/start` 能从 DB 读已发布版本；步骤级 **默认 assignee** 在能解析时写入任务。

### 5.1 数据层

- [ ] **Postgres**：新增 `migrations/0002_workbench_workflow_templates.up.sql`（表名与详细设计 §3.2 一致：`workflow_templates`、`workflow_template_versions`）。
- [ ] **SQLite**：在 `src/saas/sqlite.rs` 增加 `saas_workflow_templates`、`saas_workflow_template_versions`（或等价命名）及 `ensure_column`/初始化语句。
- [ ] **Rust 模型**：`src/saas/models.rs`（或新建 `workflow_models.rs`）定义 struct + `serde` 与 `definition_json` 解析类型。
- [ ] **仓储**：`SaasSqliteStore` 上实现 list/get/publish/create_version（方法命名与现有风格一致）；若尚无 async repository trait，可先同步方法再抽 trait。

### 5.2 内置模板合并

- [ ] 将 `workflow_product_service::list_workflow_templates` 中硬编码列表改为 **内置常量**（只读），与 DB `published` 结果 **合并**（slug 冲突策略：DB 覆盖内置或内置优先，需写死一条规则并文档化）。
- [ ] `GET /api/workflow-templates`：返回合并列表；字段保持与前端 `WorkflowTemplateSummary` 兼容，必要时扩展 `id`/`slug`/`version`。

### 5.3 专家 API（最小）

- [ ] `GET /api/admin/workflow-templates`：含 draft（权限：`OrgAdmin` 或新 Expert，与决策一致）。
- [ ] `POST /api/admin/workflow-templates`：创建模板 + v1 draft。
- [ ] `POST /api/admin/workflow-templates/:id/versions`：追加 definition。
- [ ] `POST /api/admin/workflow-templates/:id/publish`：发布指定 version。
- [ ] 所有写操作 **写 audit**（action 命名如 `workflow_template.publish`）。

### 5.4 AgentInstanceResolver

- [ ] 实现 `(team_id, agent_template_id) -> Option<agent_instance_id>` 查询（`saas_agent_instances` 或 PG 等价表）。
- [ ] `start_workflow_run` 路径：对每一步若 definition 含 `default_agent_template_id`，则解析并写入任务 assignee 字段（与当前 `Task.assignee_ids` 或未来主键字段对齐，不破坏 JSON 序列化）。

### 5.5 `POST /api/workflows/start` 改造

- [ ] 请求体支持 `template_slug` 或现有 `template_id`（兼容）；可选 `template_version`；未传则使用当前 **已发布最新版本**。
- [ ] Run 生成逻辑：从 DB definition 展开 steps；第一步 `InProgress` 等行为与现逻辑一致。
- [ ] 任务仍写入当前存储（M3 前仍为 `tasks.json`），但任务行需带 **template_version**（若 JSON 结构暂无字段，先扩 `task_service::Task` 与 serde default）。

### 5.6 前端（专家）

- [ ] 新页「工作流模板」：列表 + 创建草稿 + 编辑 JSON/表单 definition + 发布（可先做最小 JSON 文本框 + 校验提示）。
- [ ] 权限：仅管理角色可见该菜单项。

### 5.7 验证

- [ ] `cargo test` 相关模块；若有 SQLite 单测，覆盖 template CRUD。
- [ ] 手工：发布一模板 → 业务工作台起流程 → 第一步任务 assignee 非空（在已 bootstrap 前提下）。

### 5.8 验收（对齐 PRD §9）

- 专家可不改代码新增并发布模板；业务侧列表含该模板；审计可查 `workflow.start` 与 template 版本信息。

## 6. M3 — 任务单数据源与 TaskRepository

**目标**：API 读写任务经 **TaskRepository**；以 SQL 为权威；过渡期可双写/开关。

### 6.1 接口与实现

- [ ] 定义 `TaskRepository` trait（或 enum 分发）：`list`、`get`、`create`、`update`、`list_for_board`（按 scope + status 列）。
- [ ] `JsonTaskRepository`：包装现有 `load_tasks` / `save_tasks`。
- [ ] `SqlTaskRepository`：`saas_tasks` 扩展列（`workflow_run_id`、`workflow_template_id`、`template_step_index`、`parent_task_id`、`task_kind`、`artifacts_json` 等按详细设计 §3.1 分批加列）。
- [ ] **状态映射** 单模块：`task_status_to_api` / `task_status_from_db`（单元测试必填）。

### 6.2 表结构扩展

- [ ] SQLite：`ensure_column` 批量添加；迁移已有 `import_tasks` 逻辑评估是否需二次导入 `workflow_*` 字段。
- [ ] Postgres：`ALTER TABLE tasks` 与新建索引（`workflow_run_id`、`team_id`+`status`）。

### 6.3 双写与切换

- [ ] 环境变量或配置项：`TASK_PERSISTENCE=json|sql|dual_write`（命名可调整，实现与详细设计 §6.1 一致）。
- [ ] `dual_write`：写 JSON + SQL；读 SQL（或 configurable）。
- [ ] Cutover  checklist：备份 `tasks.json` → 全量导入 SQL → 切换 `sql` → 监控一周无回滚需求再删双写代码路径。

### 6.4 路由改造

- [ ] `api_tasks_list`、`api_tasks_create`、`api_tasks_update`、`api_task_board`、`api_workflows_start` 内任务持久化全部经 Repository。
- [ ] 保持 API JSON 形状兼容前端；若有 breaking， bump 或加字段 default。

### 6.5 前端

- [ ] 确认 `api-types.ts` 与后端字段一致；看板过滤 `workflow_run_id` 等若后端已支持则接 query。

### 6.6 验证

- [ ] 集成测试或脚本：创建任务 → 重启进程 → 数据仍在（SQL）。
- [ ] 性能：看板查询在 1k 任务量级粗测（可选）。

### 6.7 验收

- 无 `tasks.json` 依赖下（`TASK_PERSISTENCE=sql`），全流程起流程 + CRUD + 看板可用。

## 7. M4 — 项目与子任务派生

**目标**：`projects` 表（或等价）；`parent_task_id`；`POST /api/tasks/:id/spawn-children` + 幂等。

### 7.1 数据层

- [ ] `projects` 表（PG + SQLite DDL）。
- [ ] `tasks.project_id` FK（可空，兼容旧数据）。
- [ ] 幂等：`task_spawn_idempotency` 小表或 `domain_events` payload 存 `idempotency_key` → 子任务 ID 列表。

### 7.2 API

- [ ] `POST /api/tasks/:id/spawn-children`：校验 scope、父任务状态、body schema（PRD §11.3）。
- [ ] `GET /api/tasks?project_id=`、`workflow_run_id=` 过滤。
- [ ] 审计：`task.spawn_children`。

### 7.3 前端

- [ ] 项目列表/详情（最小）：创建项目、绑定团队、关联 run（或手动挂任务）。
- [ ] 任务详情：展示子任务树；触发「派生子任务」（若首期仅 API，可只做开发者工具或隐藏入口）。

### 7.4 验证

- [ ] 同一 `idempotency_key` 重放返回相同子任务集合。
- [ ] 子任务继承 `workflow_run_id` 默认行为与 PRD 一致。

## 8. M5（可选）— Vibecoding 扩展与 Review

**目标**：`task_kind`、artifacts、Review 报告结构、PR/CI 外链展示。

### 8.1 后端

- [ ] `PATCH /api/tasks/:id` 允许更新 `artifacts`、`execution`（`linked_pr_url`、`ci_status`、`correlation_id`）、`review_report`（四块结构）。
- [ ] 可选：`ci_status` 由 webhook 更新（单独 issue，可拆出）。
- [ ] 关闭 `code_review` 任务策略：配置项 `require_human_approval`、`require_ci_green`（产品确认后实现）。

### 8.2 前端

- [ ] 任务表单：选择 `task_kind`、添加 artifact 链接列表。
- [ ] Review 任务：结构化表单或 Markdown 上传解析（最小：JSON 文本区 + 预览）。
- [ ] 看板按 `task_kind` 筛选。

### 8.3 验证

- [ ] PRD §11.2 各类型至少一条手工用例；Review 报告字段落库可读回。
