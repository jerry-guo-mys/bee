## 0. 维护约定

- 任务以 `- [ ]` / `- [x]` 勾选；大项完成后在「里程碑状态」表打勾并填完成日期。
- 阻塞项在任务下用 `> 阻塞：` 记录原因与跟进人。
- 若范围变更：改 PRD → 改详细设计 → **再改本计划**，避免三份文档漂移。
- 建议每个里程碑结束时补一行 **Retrospective**（3 条以内：做得好的 / 需改进 / 下阶段注意）。

## 4. M1 — 信息架构与导航（无后端大改）

**目标**：用户心智上区分「工作台」与「平台管理」；现有能力可继续走原 API。

### 4.1 任务清单

- [x] **路由结构**：新增 `web-ui` 路由前缀，例如 `/workbench`（首页可为 Dashboard 或重定向到 Runs）。
- [x] **管理端归组**：将 `tenants`、`organizations`、`teams`、`members`、`audit-logs`、`tool-policies` 等归入侧边栏分组「平台管理」或 `/admin` 前缀（二选一，与详细设计 §7 一致）。
- [x] **工作台分组**：`workflows` 页面迁入 `workbench/runs` 或保留路径但导航显示为「工作台 · 流程与任务」。
- [x] **Layout**：`Layout.tsx` 更新导航项顺序与分组；可选为 workbench 使用略简化的顶栏（仍共用 scope）。
- [x] **Scope 提示**：未选 `team_id` 时，工作台核心操作（起流程）给出明确提示，引导选择 scope（沿用 `ADMIN_SCOPE_CHANGED_EVENT`）。
- [x] **文案**：页面标题、面包屑与按钮与 PRD 用语对齐（少提「工作流」技术词，多提「流程」「任务」）。
- [ ] **回归**：手动走通：选 scope → 打开原 Workflows 等价页 → 起模板 → 看板仍可用。（构建已通过；需在联调环境手测）

### 4.2 交付物

- 可合并的 PR：仅 `web-ui` + 必要静态资源；`App.tsx` 路由表更新。
- 截图或简短录屏（可选）：导航前后对比，附在 PR 描述。

### 4.3 验收（对齐 PRD §8 M1）

- 业务用户从主导航可进入工作台且不易误入租户/成员等管理页（除非权限设计允许同入口）。

## 5. M2 — 工作流模板出库表 + Resolver + start 兼容

**目标**：模板可配置；`POST /api/workflows/start` 能从 DB 读已发布版本；步骤级 **默认 assignee** 在能解析时写入任务。

### 5.1 数据层

- [x] **Postgres**：新增 `migrations/0002_workbench_workflow_templates.up.sql`（表名与详细设计 §3.2 一致：`workflow_templates`、`workflow_template_versions`）。
- [x] **SQLite**：在 `src/saas/sqlite.rs` 增加 `saas_workflow_templates`、`saas_workflow_template_versions`（或等价命名）及 `ensure_column`/初始化语句。
- [x] **Rust 模型**：`src/saas/workflow_template.rs` 定义 struct + `serde` 与 `definition_json` 解析类型。
- [x] **仓储**：`SaasSqliteStore` 上实现 list/get/publish/create_version（方法命名与现有风格一致）；若尚无 async repository trait，可先同步方法再抽 trait。

### 5.2 内置模板合并

- [x] 将 `workflow_product_service::list_workflow_templates` 中硬编码列表改为 **内置常量**（只读），与 DB `published` 结果 **合并**（slug 冲突策略：**租户已发布覆盖内置**）。
- [x] `GET /api/workflow-templates`：返回合并列表；字段保持与前端 `WorkflowTemplateSummary` 兼容，必要时扩展 `id`/`slug`/`version`。

### 5.3 专家 API（最小）

- [x] `GET /api/admin/workflow-templates`：含 draft（权限：`OrgAdmin` 或新 Expert，与决策一致）。
- [x] `POST /api/admin/workflow-templates`：创建模板 + v1 draft。
- [x] `POST /api/admin/workflow-templates/:id/versions`：追加 definition。
- [x] `POST /api/admin/workflow-templates/:id/publish`：发布指定 version。
- [x] 所有写操作 **写 audit**（action 命名如 `workflow_template.publish`）。

### 5.4 AgentInstanceResolver

- [x] 实现 `(team_id, agent_template_id) -> Option<agent_instance_id>` 查询（`saas_agent_instances` 或 PG 等价表）。
- [x] `start_workflow_run` 路径：对每一步若 definition 含 `default_agent_template_id`，则解析并写入任务 assignee 字段（与当前 `Task.assignee_ids` 或未来主键字段对齐，不破坏 JSON 序列化）。

### 5.5 `POST /api/workflows/start` 改造

- [x] 请求体支持 `template_slug` 或现有 `template_id`（兼容）；可选 `template_version`；未传则使用当前 **已发布最新版本**。
- [x] Run 生成逻辑：从 DB definition 展开 steps；第一步 `InProgress` 等行为与现逻辑一致。
- [x] 任务仍写入当前存储（M3 前仍为 `tasks.json`），但任务行需带 **template_version**（若 JSON 结构暂无字段，先扩 `task_service::Task` 与 serde default）。

### 5.6 前端（专家）

- [x] 新页「工作流模板」：列表 + 创建草稿 + 编辑 JSON/表单 definition + 发布（可先做最小 JSON 文本框 + 校验提示）。
- [x] 权限：仅管理角色可见该菜单项。

### 5.7 验证

- [x] `cargo test` 相关模块；若有 SQLite 单测，覆盖 template CRUD。
- [ ] 手工：发布一模板 → 业务工作台起流程 → 第一步任务 assignee 非空（在已 bootstrap 前提下）。

### 5.8 验收（对齐 PRD §9）

- 专家可不改代码新增并发布模板；业务侧列表含该模板；审计可查 `workflow.start` 与 template 版本信息。

## 6. M3 — 任务单数据源与 TaskRepository

**目标**：API 读写任务经 **TaskRepository**；以 SQL 为权威；过渡期可双写/开关。

### 6.1 接口与实现

- [x] `TaskRepository` trait + `WorkspaceTaskRepo`；`patch_task` 仍为模块级函数（闭包更新）；列表/读/写/追加走 trait 或同模块自由函数。
- [x] JSON 路径：包装现有 `load_tasks` / `save_tasks`（`TaskPersistenceMode::Json`）。
- [x] SQL 路径：`saas_tasks` 已加列 `workflow_run_id`、`workflow_template_id`、`workflow_template_version`、`assignee_ids_json`、`group_id`、`coordinator_id`、`internal_group`（`template_step_index` / `parent_task_id` / `task_kind` 等留待 M4/M5）。
- [x] **状态映射**：`task_status_to_db` / `task_status_from_db` + 单测。

### 6.2 表结构扩展

- [x] SQLite：`ensure_column` 批量添加；旧 `import_tasks` 行可在下次打开 DB 时用新列存 NULL，新写入走完整 upsert。
- [x] Postgres：`migrations/0003_workbench_task_columns.{up,down}.sql`（`workflow_*`、`assignee_ids_json`、`group_id`、`coordinator_id`、`internal_group` + 索引）。

### 6.3 双写与切换

- [x] 环境变量：`TASK_PERSISTENCE`（优先）与 `BEE_TASK_PERSISTENCE`：`json` | `sql` | `dual_write`。
- [x] `dual_write`：写 SQL + 全量回写 `tasks.json`；读 SQL。
- [x] Cutover 清单：见 [开发进度](./工作台需求-开发进度.md)「M3 — 切换 SQL 数据源（Cutover）」。

### 6.4 路由改造

- [x] `api_tasks_list`、`api_tasks_create`、`api_tasks_update`、`api_task_board`、`api_workflows_start` 与 `task_coordinator_service` 经 `task_repository` / `TaskRepository`。
- [x] API JSON 与前端类型兼容（仅增字段与 query，无破坏性改名）。

### 6.5 前端

- [x] `api-types.ts` 与后端 `Task` 一致；`getTasks` 支持 `workflow_run_id` query（与 `GET /api/tasks?workflow_run_id=` 对齐）。

### 6.6 验证

- [x] 集成级单测：`sql_task_survives_db_reopen`、`workspace_task_repo_implements_trait`（`cargo test -p bee --features web --bin bee-web task_repository`）。
- [ ] 性能：看板 1k 任务量级粗测（可选，未阻塞 M3）。

### 6.7 验收

- [ ] 运维手工：设 `TASK_PERSISTENCE=sql`，起流程 + CRUD + 看板（依赖环境中有合法 tenant/org/team 外键数据）。

## 7. M4 — 项目与子任务派生

**目标**：`projects` 表（或等价）；`parent_task_id`；`POST /api/tasks/:id/spawn-children` + 幂等。

### 7.1 数据层

- [x] `projects` 表（PG + SQLite DDL）。
- [x] `tasks.project_id`（PG 为 FK；SQLite `saas_tasks` 增加 `project_id` / `parent_task_id` 列，兼容旧数据）。
- [x] 幂等：`task_spawn_idempotency`（PG）+ `saas_task_spawn_idempotency`（SQLite）记录 `idempotency_key` → 子任务 ID 列表。

### 7.2 API

- [x] `POST /api/tasks/:id/spawn-children`：校验 scope、父任务状态、body schema（PRD §11.3）。
- [x] `GET /api/tasks?project_id=`、`workflow_run_id=` 过滤。
- [x] 审计：`task.spawn_children`。

### 7.3 前端

- [x] 项目列表/详情（最小）：`/workbench/projects` 创建项目、按 scope 列表展示并可关联 run。
- [x] 任务详情派生入口：首期按“API/开发者工具”落地（`spawnChildren` API 封装）；任务树 UI 留待 M4.1（不阻塞后端主链）。

### 7.4 验证

- [x] 同一 `idempotency_key` 重放返回相同子任务集合（API 幂等表返回已落库 child IDs）。
- [x] 子任务继承 `workflow_run_id` 默认行为与 PRD 一致（`inherit_workflow_run_id` 默认 true）。

## 8. M5（可选）— Vibecoding 扩展与 Review

**目标**：`task_kind`、artifacts、Review 报告结构、PR/CI 外链展示。

### 8.1 后端

- [x] `PATCH /api/tasks/:id` 允许更新 `artifacts`、`execution`（`linked_pr_url`、`ci_status`、`correlation_id`）、`review_report`（四块结构，JSON 透传）。
- [x] `ci_status` webhook：`POST /api/tasks/:id/ci-status` 回写 `execution.ci_status`（可带 `correlation_id`、`linked_pr_url`）。
- [x] `code_review` 关闭策略：环境变量 `REQUIRE_HUMAN_APPROVAL`、`REQUIRE_CI_GREEN` 控制 `status=done` 校验。

### 8.2 前端

- [x] 任务表单：支持选择 `task_kind`（创建任务时）。
- [x] Review 任务最小输入：JSON 文本区（`review_report`），创建时可提交；Markdown 解析留后续。
- [x] 看板/列表按 `task_kind` 筛选（`GET /api/tasks?task_kind=`，工作台筛选下拉）。

### 8.3 验证

- [ ] PRD §11.2 各类型至少一条手工用例；Review 报告字段落库可读回。
