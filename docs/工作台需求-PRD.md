## 1. 背景与目标

### 1.1 背景

希望在现有 Bee 能力之上，形成可对外呈现的两层产品形态：

- **业务工作台**：项目经理与执行同学管理「项目 / 任务 / 执行状态」，在已发布的能力范围内驱动多 Agent 协作，不接触提示词与工具底层配置。
- **专家能力（治理层）**：少数内部角色维护 **Agent 模板与实例策略**、**工作流模板** 及团队绑定，保证安全、一致与可审计。

当前仓库已具备 **SaaS 多租户数据模型**、**管理端 API 与 Web UI（租户/组织/团队/成员/审计等）**、**工作流模板列表与一键起流程（推任务）**、**文件型任务持久化与看板**、**团队 Agent 实例 bootstrap** 等能力，但存在 **「库表能力」与「运行时任务/工作流」未贯通**、**模板硬编码**、**步骤与 Agent 角色未绑定** 等断层。本 PRD 明确如何 **复用现有功能** 并在同一迭代中 **收敛技术债**。

### 1.2 目标（可验收）

1. 业务用户能在 **统一工作台** 内完成：选团队上下文 → 建项目或起工作流 → 查看/更新任务 → 触发执行（与现有会话或任务启动链路衔接）。
2. 专家用户能在 **治理视图** 内完成：维护租户级 Agent 模板与团队实例、维护可发布的工作流模板（版本化），业务侧仅可选用已发布版本。
3. **任务与工作流** 与 **租户/组织/团队** 作用域一致，审计可追溯；逐步 **对齐** `migrations/0001_init_saas_schema.up.sql` 中的 `tasks` / 会话等设计，替代或同步「仅 workspace 文件」的单一数据源（见第 6 节）。

### 1.3 非目标（本阶段可明确排除）

- 业务用户自定义工作流结构、任意修改 Agent 工具白名单。
- 完整可视化 DAG 编排器（可作为后续阶段）。
- 跨租户模板市场。

## 2. 用户与权限

### 2.1 角色

| 角色 | 主要职责 |
|------|----------|
| 租户/组织管理员 | 成员与组织治理、管理端入口控制。 |
| **Agent/流程专家** | 维护 `agent_templates`、团队 `agent_instances`、工作流模板发布与版本；配置 `tool_policies` 等与安全相关的策略。 |
| **业务用户（PM/执行）** | 在团队/项目上下文中创建与跟进任务；从已发布工作流模板「起流程」；分配任务到 **已定义的 Agent 角色/实例**（不允许改模板与工具集）。 |

### 2.2 权限原则

- 工作流模板与 Agent 定义的 **写权限** 默认仅专家与管理角色；业务侧 **只读 + 选用**。
- 项目启动时 **钉死** 所选用工作流模板版本；专家升级模板不静默改变进行中项目的解释行为（除非显式「升级」操作）。

---

## 3. 核心概念（产品名词）

- **项目**：业务侧容器，关联组织/团队、选用工作流模板版本（可选）、聚合任务与里程碑。
- **工作流模板（可发布）**：多步骤流程定义；每一步建议映射到 **步骤说明 + 默认承接 Agent 角色（模板 ID 或实例槽位）**。
- **工作流运行（run）**：一次「起流程」产生的实例，带 `workflow_run_id`，下辖多条任务。
- **任务**：可列在看板上的单元；含状态、描述、可选依赖、承接 Agent、与一次或多次 **执行运行** 的关联。
- **Agent 模板 / 团队实例**：与现有 SaaS 表 `agent_templates`、`agent_instances` 及 API `GET /api/agent-templates`、`POST /api/teams/:team_id/agent-instances/bootstrap` 对齐。

## 4. 与现有功能的映射：如何「用起来」

### 4.1 SaaS 多租户与团队

| 现有能力 | 工作台中的用途 |
|----------|----------------|
| `tenants` / `organizations` / `teams` / `memberships` | 全局作用域；业务工作台顶部的 **当前租户/组织/团队** 与成员权限（与现有 admin scope 一致）。 |
| Web：`/tenants`、`/organizations`、`/teams`、`/members` | **治理侧**基础；工作台仅消费「当前用户可见团队列表」，不必把业务用户导向全部管理页。 |
| `audit_logs` | 记录工作流启动、任务状态变更、专家配置变更；与现有 `write_audit_log` 路径统一字段语义。 |

### 4.2 Agent 模板与团队实例

| 现有能力 | 工作台中的用途 |
|----------|----------------|
| `agent_templates`（库表）+ `GET /api/agent-templates` | 专家维护；业务侧 **选角色** 时展示已发布模板列表（名称、描述摘要，不暴露完整 prompt 亦可配置）。 |
| `POST /api/teams/:team_id/agent-instances/bootstrap` | 团队具备可执行任务前，由专家完成实例化；业务工作台在执行前可检测「未 bootstrap」并提示联系专家。 |
| `tool_policies` / `membership_tool_policies` | 专家配置工具边界；任务执行时运行时 enforcement 与现有 Tool Router / policy 方向一致。 |

### 4.3 工作流「推任务」

| 现有能力 | 工作台中的用途 |
|----------|----------------|
| `GET /api/workflow-templates` + `POST /api/workflows/start` | 业务侧 **起流程** 主入口；请求体已支持 `tenant_id` / `organization_id` / `team_id`（与 scope 对齐）。 |
| `workflow_product_service::list_workflow_templates` | 现为 **进程内硬编码** 模板；产品上视为「内置示例」——专家发布模板后应 **迁出为可配置数据源**（见第 6 节）。 |
| `workflow_run_id`、`workflow_template_id` 写入 `Task`（`task_service.rs`） | 用于看板分组、按 run 过滤、与子任务派生关联；**保留并强化** 为项目视图的第一级分组维度。 |

### 4.4 任务与看板

| 现有能力 | 工作台中的用途 |
|----------|----------------|
| `GET /api/task-board`（按列聚合） | 业务工作台 **默认看板** 数据源；继续按 `tenant_id` / `organization_id` / `team_id` 过滤。 |
| `GET/POST /api/tasks`、`PATCH /api/tasks/:id`、`POST /api/tasks/:id/start` | 单任务 CRUD 与执行触发；与工作台任务详情、重新运行衔接。 |
| `tasks.json` + `Task` 结构（`assignee_ids`、`coordinator_id` 等） | **当前事实存储**；与库表 `tasks`（`assignee_agent_id`、`session_id` 等）存在字段与持久化 **双轨**（见第 6 节统一策略）。 |

### 4.5 前端现状

| 现有页面 | 建议 |
|----------|------|
| `web-ui/src/pages/Workflows.tsx` | 已具备模板选择、起工作流、看板/列表；作为 **业务工作台** 的核心之一，导航与文案上归入「工作台」而非仅「工作流」技术名。 |
| Dashboard / Agents / Tool policies 等 | **专家或高级用户**入口；与工作台信息架构拆分，避免业务用户误入高风险配置。 |

## 5. 功能需求摘要

### 5.1 业务工作台（MVP）

1. **上下文**：进入工作台须带有效管理 scope（租户/组织/团队），与现有 `ADMIN_SCOPE_CHANGED_EVENT` 一致。
2. **起流程**：从 **已发布** 工作流模板列表选择 → 填写标题/描述 → 调用 `POST /api/workflows/start` → 看板展示新 run 下任务。
3. **任务管理**：列表/看板查看、筛选（按 run、按状态）、更新状态、补充描述；可选 **简单依赖**（后续迭代可加重）。
4. **分配**：将任务指派到 **团队内已存在的 agent instance**（或「角色」解析到实例）；若映射未配置，提示专家补齐模板/实例。
5. **执行**：沿用 `POST /api/tasks/:id/start`（或与会话入口合并），界面展示运行状态与结果摘要。
6. **子任务派生（P1 可并入 MVP 后半）**：任务完成时支持结构化「子任务建议」写入新任务，并继承 `workflow_run_id` 或项目 ID；**任务类型、标准交付物与 Vibecoding 全流程对齐见第 11 节**。

### 5.2 专家侧（与现有管理端合并演进）

1. **Agent 模板 CRUD**（API 已有列表；补全创建/更新/版本若缺失）与 **团队 bootstrap** 操作指引。
2. **工作流模板管理**：从硬编码迁移为 **租户可配置**（至少 JSON/表单存储），含步骤列表、每步 **默认 agent_template_id**、发布标记与版本号。
3. **权限**：管理端路由与 API 的 `AccessRequirement` 与角色对齐，区分 TeamAdmin / OrgAdmin 与未来的 Expert 角色。

### 5.3 项目（建议 P1 明确数据模型）

- 引入 **项目** 实体（可新建表或与 `workflow_run` 轻量聚合）：业务用户「新建项目」→ 绑定团队 → 关联多个 run 与零散任务。
- MVP 可用 **「一次 run = 逻辑项目」** 过渡，避免阻塞工作台首版。

## 6. 现状问题与本次一并优化（技术债与方案方向）

以下问题建议在「工作台」里程碑中 **分阶段消化**，避免长期双写双读失控。

| # | 问题 | 影响 | 建议方向 |
|---|------|------|----------|
| 1 | 工作流模板硬编码于 `workflow_product_service.rs` | 无法按租户差异化；与「专家维护」矛盾 | 模板入库或至少租户级配置表；代码内保留少量系统内置模板 ID |
| 2 | 任务仅存 `tasks.json` | 与 `migrations` 中 `tasks` 表脱节；多实例/备份/查询弱 | 以 **SQL 为权威** 或明确 **同步层**；API 统一从一处读 |
| 3 | `start_workflow_run` 中 `assignee_ids` 为空 | 步骤与 Agent 无绑定，业务无法「谁做什么」 | 模板每步增加 `default_agent_template_id`，bootstrap 后解析为 `agent_instance_id` 写入任务 |
| 4 | `team_hint` 仅为字符串 | 与真实 `teams` 无关联 | 改为可选 `team_code` 或模板级「适用团队」元数据，仅作筛选提示 |
| 5 | 库表 `tasks` 字段（`session_id`、`assignee_agent_id`）与 JSON `Task` 不一致 | 模型分裂，集成会话困难 | 统一领域模型 DTO；迁移脚本或适配层映射 |
| 6 | 动态 `agents.json` 与 SaaS `agent_instances` 并存 | 用户困惑「哪个是真相」 | 产品文档与 UI 标明：团队执行以 **实例化后的 SaaS 实例** 为主；动态 agent 逐步收敛场景 |
| 7 | 管理页与业务看板混在同级路由 | 业务用户易误入 | 导航分组：「工作台」与「平台管理」 |

## 7. 非功能需求

- **审计**：工作流启动、任务关键状态变更、模板发布与 Agent 变更写入 `audit_logs`（或等价 workspace audit），字段包含 `tenant_id` / `organization_id` / `team_id`。
- **隔离**：任意列表接口默认按当前 scope 过滤，禁止跨团队数据泄露。
- **可观测**：任务执行与 LLM run 建议共享 trace/correlation id（与现有 observability 方向一致，可分阶段）。
- **幂等**：重复「完成」回调、重复启动同一任务需安全 noop 或可配置策略。

|------|--------|

## 9. 验收标准（M1–M2 示例）

1. 业务用户在选定团队 scope 下，可仅通过工作台完成：浏览已发布模板 → 启动工作流 → 在看板看到带 `workflow_run_id` 的任务组。
2. 专家用户可新增/编辑至少一条租户级工作流模板（非改代码），且业务侧可见列表来源于该配置。
3. 启动工作流后，至少第一步任务可自动或半自动带有 **有效 assignee**（当团队已完成对应模板的 instance bootstrap）。
4. 审计中可检索到对应 `workflow.start` 及任务创建记录。

## 11. 与 Vibecoding 协作流对齐

本节说明：日常 **vibecoding**（页级需求 → 详设 → 拆任务 → 前后端开发 → Code Review → 调试复盘）能否由工作台承载，以及需要 **显式约定的任务类型与交付物**；避免退化为仅有看板、没有方法论。

### 11.1 流程总览

典型端到端链路与工作台映射如下：

1. **需求 / PRD**：项目或 run 下创建任务，**产出物**为定稿文档（仓库路径、附件或外链）；任务状态「完成」表示需求已冻结版本。
2. **详细设计**：单独任务或子流程；产出物为设计说明（接口契约、数据模型、关键决策）；可 **派生子任务** 对应各模块实现。
3. **实现（前后端等）**：按页面或 feature 拆任务，绑定 **开发向 Agent 角色**（专家已配置工具白名单与仓库范围）。
4. **Code Review**：独立任务类型；产出物为 **结构化审查报告**（见 11.4）。
5. **联调与缺陷**：缺陷任务可挂父任务/run；关闭条件含复现步骤与修复说明摘要。
6. **经验沉淀**：独立 **复盘 / Lessons** 任务或固定文档槽位，避免经验只留在会话里（见 11.5）。

### 11.2 标准协作任务类型与交付物

建议在任务上增加 **`task_kind`（或标签）** 与 **`artifacts` 列表**（URI + 类型），便于筛选与验收。首版可用约定枚举 + 自由文本，后续再收紧 schema。

| `task_kind` | 说明 | 标准交付物（示例） | 验收提示 |
|-------------|------|-------------------|----------|
| `requirement` | 需求 / PRD 定稿 | `docs/...` 路径、Notion/飞书链接、版本号 | 业务与专家确认「已发布」 |
| `design` | 详细设计 | 设计文档、API 草案、关键时序说明 | 覆盖接口与数据边界 |
| `implement` | 功能开发（含前后端一页） | PR 链接、commit 范围说明 | CI 通过（见 11.4） |
| `code_review` | 代码审查 | 结构化 Review 报告（Markdown/JSON） | 必改项清零或已登记豁免 |
| `bugfix` | 缺陷修复 | 根因、修复说明、回归方式 | 关联原缺陷任务 |
| `retro` | 复盘 / 经验记录 | Lessons 文档或知识库条目 | PM 或负责人确认已入库 |

专家可在 **工作流模板** 中预置上述阶段顺序与默认承接角色；业务侧 **不可改模板结构**，仅创建 run 与在允许范围内调整任务指派。

### 11.3 子任务派生（结构化输出）

父任务（尤其是 `design` 或 `implement`）完成时，执行 Agent 或人类可提交 **子任务建议列表**，服务端校验后批量创建子任务。建议最小 JSON 字段约定（与实现阶段字段名可对齐）：

- `title`（必填）、`description`、`task_kind`
- `assignee_agent_instance_id` 或 `assignee_role`（由编排解析为实例）
- `depends_on_task_ids`（可选）
- `acceptance_criteria`（可选，短文本）
- `inherit_workflow_run_id`：默认 true，子任务继承当前 run / 项目上下文

**幂等**：同一父任务 + 同一批建议内容的重复提交应 noop 或可配置为「追加仅新项」。

### 11.4 Code Review：扫库、修/不修判定、总报告与 CI 分工

- **工作台内 Review 任务** 的交付物建议固定包含四块：**必改（blocking）**、**建议改（non-blocking）**、**不修/豁免（wont_fix + 理由）**、**技术债 backlog（可选跟进）**。
- **Agent 能力边界**：Review Agent 以只读扫库 + 项目约定检查（如 `cargo fmt --check`、`cargo clippy`、测试命令、安全/风格 checklist）为主，生成报告；**「不修」类结论默认需人类在任务评论或审批中确认**，避免模型单方面放行风险项。
- **与 CI 的关系**：**格式化、lint、单测等门禁以 CI 为权威**；工作台展示「关联 commit/PR 的 CI 状态」。Agent Review 报告 **补充** 语义与设计层问题，**不替代** CI。二者在任务详情中并列展示，减少「报告全绿但 CI 未跑」的误判。

可选字段：`linked_pr_url`、`linked_commit_sha`、`ci_status`（由 webhook 或轮询更新，分阶段实现）。

### 11.5 调试经验如何记录

工作台 **不会自动** 总结调试经验；需产品化一种轻量习惯，任选或组合：

1. **复盘任务（`task_kind = retro`）**：联调或事故结束后创建，交付物为固定模板短文（现象 → 根因 → 修复 → 预防）。
2. **项目级 Lessons 文档**：在项目中维护单一入口（如 `docs/projects/<id>/LESSONS.md`），每条重大调试在对应任务完成时更新并 **在任务 artifact 中链接**。
3. **领域事件 / 审计**：关键事故写入 `domain_events` 或 `audit_logs` 的 `detail_json`（摘要级），便于检索而非全文知识库。

推荐 **1 + 2** 并行：任务可追溯，文档可沉淀为团队记忆。

### 11.6 与工作台产品目标的关系

- 本节不改变第 2 节权限模型：**模板与 Agent 配置仍由专家维护**；业务侧使用预置的「Vibecoding 标准工作流」即可跑通全链路。
