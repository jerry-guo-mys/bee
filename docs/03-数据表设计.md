# 1. 文档目标

本文档用于输出 **AI 多 Agent 协作平台** 的数据库与表结构设计草案。
目标不是一次性把所有字段定死，而是给架构师和研发团队提供一个清晰的建模基础。

本文档重点解决以下问题：

1. 平台中有哪些核心数据对象
2. 每个核心对象建议有哪些字段
3. 对象之间的关系是什么
4. 哪些字段是强业务字段，哪些字段可以后续扩展
5. 哪些表适合高频读写，哪些表更偏审计与分析
6. 哪些地方需要做版本化、快照化、日志化

---

# 2. 设计原则

---

## 2.1 配置与运行分离

平台中存在两类非常不同的数据：

### 第一类：配置数据

例如：

* Agent 定义
* Team 定义
* Workflow 定义
* Prompt 配置
* Tool 配置
* 策略配置

这些数据的特点是：

* 修改频率相对低
* 对一致性要求高
* 需要版本管理
* 需要支持发布与回滚

---

### 第二类：运行数据

例如：

* Task
* TaskStep
* TraceLog
* ApprovalRecord
* EvalRecord

这些数据的特点是：

* 写入频繁
* 需要保留执行现场
* 需要支持查询、追踪、回放
* 后期可能数据量非常大

所以数据库设计上必须把：

```text
配置态
与
运行态
```

拆开考虑。

---

## 2.2 当前配置与历史快照分离

很多对象，例如 Agent、Workflow，在被任务执行时，不能只引用“当前最新版本”，而应该引用：

> **任务创建当时的配置快照**

否则会出现问题：

* 今天执行的任务引用了昨天的 Agent 配置
* 后续 Agent 被修改后，历史任务无法复现
* replay 失真

所以建议：

* 配置主表保存当前版本
* 版本表保存历史版本
* Task / TaskStep 运行时绑定快照版本号，必要时保存快照副本

---

## 2.3 审计与业务查询分层

有些表主要用于：

* 前台页面查询
* 业务状态推进

有些表主要用于：

* 审计
* replay
* 问题排查
* 离线分析

这些表不能混用，否则会影响性能。

---

## 2.4 Memory 不等于聊天记录

Memory 设计要明确分层：

* Task Memory：任务现场
* Agent Memory：个人画像 / 历史经验摘要
* Team Memory：团队共享规则 / 知识

这三类不能混成一张表。

---

## 2.5 Growth / Eval 建议和原始事件分离

原始事件：

* 某次任务结果
* 某次人工反馈
* 某次评分

画像和成长结论：

* 该 Agent 最近擅长什么
* 哪类任务失败多
* 当前建议如何优化

也不能混在一起。
建议：

* 原始表保存事实
* 聚合表保存画像

# 4. 核心实体关系总览

下面先用业务语言讲关系，再给建议表。

---

## 4.1 关键关系

### Agent 与 Team

* 一个 Team 可以包含多个 Agent
* 一个 Agent 可以被多个 Team 复用
* 所以是多对多关系

---

### Workflow 与 Team

* 一个 Team 可以绑定多个 Workflow
* 一个 Workflow 主要归属于一个 Team
* 一对多关系

---

### Workflow 与 Node

* 一个 Workflow 有多个节点
* 一个节点属于一个 Workflow
* 一对多关系

---

### Task 与 Workflow

* 一个 Task 执行时选择一个 Workflow
* 一个 Workflow 可产生多个 Task
* 一对多关系

---

### Task 与 TaskStep

* 一个 Task 包含多个 TaskStep
* 一个 Step 只属于一个 Task
* 一对多关系

---

### TaskStep 与 Agent

* 一个 Step 通常由一个 Agent 负责
* 一个 Agent 可以执行很多 Step
* 多对一关系

---

### Task / Step 与 Approval

* 一个 Task 的某个 Step 可能触发多次审批
* 一对多关系

---

### Agent 与 Growth / Memory

* 一个 Agent 对应多个原始记忆事实
* 一个 Agent 对应一个或多个阶段性画像
* 一对多关系

---

# 5.1 agent

## 5.1.1 表用途

保存 Agent 的主定义信息，表示“当前这个 Agent 是谁”。

## 5.1.2 建议字段

| 字段              | 类型            | 说明                                   |
| --------------- | ------------- | ------------------------------------ |
| id              | bigint / uuid | 主键                                   |
| agent_code      | varchar(64)   | Agent 唯一编码                           |
| agent_name      | varchar(128)  | Agent 名称                             |
| description     | text          | Agent 描述                             |
| role_type       | varchar(64)   | 角色类型，如 writer / reviewer / architect |
| scenario_type   | varchar(64)   | 适用场景，如 content / prd / design        |
| status          | varchar(32)   | draft / active / inactive / archived |
| current_version | int           | 当前生效版本号                              |
| owner_id        | varchar(64)   | 创建人/负责人                              |
| created_at      | datetime      | 创建时间                                 |
| updated_at      | datetime      | 更新时间                                 |
| deleted_flag    | tinyint       | 逻辑删除标志                               |

## 5.1.3 说明

这张表只描述 Agent 的“主身份”。
像 prompt、策略、工具等详细配置，不建议全塞在这里。

# 15. 数据建模重点提醒

---

## 15.1 TaskStep 不要只存最终状态

一定要保留：

* 重试次数
* 开始结束时间
* 失败原因
* 关联输出
* 关联 trace

否则后续很难排查问题。

---

## 15.2 Agent Memory Profile 不要替代原始事实

画像表只能做摘要。
原始事实仍需要保留在：

* agent_memory_fact
* human_feedback
* eval_record

否则画像失真后无法回溯。

---

## 15.3 Workflow Graph 最好“双存储”

建议：

* `workflow_version.graph_definition` 存整体图 JSON
* `workflow_node / workflow_edge` 存拆分结构

这样兼顾：

* 页面快速渲染
* 运行时高效查询
* 后续变更分析

---

## 15.4 output_content 与 output_structured 可同时存在

因为很多结果既需要：

* 给人看
* 也需要给系统做下一步处理

所以建议同时存：

* `output_content`
* `output_structured`

# 18. 给架构师的落地建议

这部分是最关键的“下一步”。

---

## 18.1 先定主键方案

建议尽早统一：

* 是用 bigint snowflake
* 还是 uuid / ulid

如果是 Java + MySQL 体系，通常可以优先：

* 业务主表：bigint snowflake
* 也可增加可读编号如 task_no

---

## 18.2 先定 JSON 字段边界

建议把这些字段先约定成 JSON：

* output_schema
* strategy_config
* tool_binding_config
* knowledge_binding_config
* graph_definition
* input_payload
* output_structured
* detail_json

这样 MVP 推进会快很多。

---

## 18.3 先定运行态与分析态分离策略

后期如果任务量大，建议：

* 运行主库负责 task / step / approval
* 日志与分析库负责 trace / llm_log / eval / growth

---

## 18.4 先定快照策略

这是 replay 的核心。
建议至少保证：

* task 绑定 workflow_version_no
* task_step 绑定 agent_version_no
* llm_call_log 存 prompt_snapshot
* memory_injection_log 存 injection_snapshot

---

# 19. 总结

这一版数据库草案的核心目标是：

> 把平台拆成“配置态 + 运行态 + 记忆态 + 审批态 + 评估态 + 审计态”六层数据结构。

最关键的设计思想是：

1. **配置与运行分离**
2. **版本与快照并存**
3. **原始事实与成长画像分离**
4. **任务现场记忆、个人记忆、团队记忆分离**
5. **观测和回放能力从第一天就要考虑**

一句话总结：

> **这不是普通业务表设计，而是在为“数字团队”的配置、运行、记忆、成长和审计搭底座。**
