# 从 Prompt 驱动到四层治理：Bee 的工具路由稳定性改造

## 引子

做 Agent 的人很快都会遇到同一类问题：

- 用户问外部 GitHub 仓库架构，系统却去 `ls` 本地目录
- 用户问“今天有什么新闻”，结果返回几天前的内容
- 用户问天气，系统先去搜 Wikipedia
- 明明已经有专用工具，模型还是绕去通用搜索

这些问题表面上各不相同，但底层往往是同一个原因：工具调用太依赖模型“临场发挥”，缺少运行时治理。

在 Bee 这轮改造里，我们把工具选择从“主要靠 prompt”升级成了一套四层治理结构。目标不是让模型永远不犯错，而是把错误限制在一个可控、可观测、可回归的范围里。

## 一、为什么 Prompt 不够

很多系统在早期都会尝试一条自然路径：把工具描述写清楚、把系统提示词写长，希望模型学会选对工具。

这当然有帮助，但效果很有限。

原因很简单：模型做工具选择时，并不是严格执行一个规则系统，而是在上下文里做语言模式匹配。只要工具之间有重叠、上下文里夹杂了记忆和恢复提示、任务本身又带一点歧义，工具路由就会开始漂。

所以真正的问题不是“工具描述写得够不够好”，而是：

- 有没有先把高确定性问题从 Planner 手里拿出来
- 有没有在运行时缩小候选工具集
- 有没有在执行前做 rewrite 和 guard
- 有没有在结果出来后判断“现在可以收口了”
- 有没有路径级回归测试来防止退化

这就是四层治理要解决的事情。

## 二、第一层：分流层

分流层负责处理那些“根本不需要 Planner 自由发挥”的请求。

例如：

- 天气
- 新闻
- 汇率
- 股价/行情
- 体育比分

这些请求有几个共同点：

- 意图强确定性
- 输入模式稳定
- 输出高度结构化
- 用户对时效性和正确性很敏感

在这种场景下，让 Planner 先思考一轮，再在 `search`、`browser`、`deep_search` 之间做选择，实际上是在制造不必要的不确定性。

所以 Bee 新增了 deterministic router。命中高确定性场景时，直接调用专用工具，跳过 Planner。

这带来的收益很直接：

- 更快
- 更省 token
- 更少绕路
- 更少恢复链

这一步的经验很明确：不是所有请求都值得走完整 ReAct。

## 三、第二层：约束层

约束层的任务，是在进入推理阶段之前，把 Planner 的决策空间压缩到足够小。

这轮改造里，我们扩展了工具 metadata，不再只记录：

- scope
- intent
- risk
- freshness

而是进一步加入：

- capability group
- capability subgroup
- latency class
- token cost class
- api cost class
- overall cost class
- preferred rank

这样 metadata 就不再只是“工具说明书”，而变成了“路由决策输入”。

然后在策略层做三件事：

1. 先按 query kind 做适配过滤
2. 再按 capability 和成本排序
3. 最后最多只给 Planner 3 到 5 个候选工具

这是一个非常重要的变化。因为很多错误不是模型“完全不懂”，而是当你把十几个长得都差不多的工具一起塞给它时，它只能用最脆弱的词面启发式来选。

减少候选集，往往比优化 prompt 更有效。

## 四、第三层：反馈层

很多 Agent 会给自己配一个 Critic，用来检查工具结果是否合理。这个方向本身没问题，但 Critic 很容易变成“杠精”。

Bee 之前也有类似问题：

- 工具结果其实已经够回答了
- 但 Critic 仍然要求“再搜一下”
- Planner 被迫继续搜索
- 最终看起来像系统一直在努力，但没有明显增益

所以这一轮把 Critic 改成了 score-based，而不是“直接下命令”。

现在 Critic 返回的是：

- `score`
- `reason`
- `retry_recommended`
- `blocking_risk`

运行时只在低于阈值时才考虑纠偏，而且还有限制重试预算。

这个变化背后的原则很重要：

Critic 应该提供风险信号，而不是替 Planner 发号施令。

一个好的 Critic，应该减少无意义搜索，而不是放大它。

## 五、第四层：守卫层

这是很多 Agent 项目容易忽略的一层。

如果没有路径级回归测试，你修好的问题很可能在下一次模型升级、prompt 调整、工具新增之后悄悄回来。

所以 Bee 加入了 Golden Dataset，不只测试输入输出，还测试：

- query kind 是否正确
- 是否应该 direct route
- 候选工具集合是否正确
- 哪些工具必须禁止
- 这类请求是否允许使用长期记忆

这比单个工具的单元测试更重要，因为它真正保护的是“系统路径”，而不是某个局部函数。

一句话说，守卫层解决的不是“这个工具能不能工作”，而是“系统会不会又开始绕路”。

## 六、这套方案带来了什么变化

落地之后，Bee 的工具调用行为发生了几个明显变化：

- 天气、新闻、汇率、行情、比分不再默认漂到通用搜索
- 外部 GitHub 仓库分析不会轻易退化到本地文件工具
- Planner 不再看到一整片平铺工具，而是看到收敛后的少量候选
- Critic 更克制，不再频繁推动继续搜索
- 坏路径开始被 Golden Dataset 固化
- 关键路由行为开始具备观测指标

这些变化看起来分散，但其实都指向同一个方向：把 Agent 从“靠模型猜工具”推进到“受运行时系统治理”。

## 七、最值得分享的经验

如果把这轮改造压缩成几条最有价值的经验，我会总结为：

1. 先分流，再规划。高确定性任务不要一律交给 Planner。
2. Metadata 要参与决策，而不是只参与展示。
3. 候选工具越少，Planner 越稳定。
4. Critic 要克制，最好打分而不是直接要求重做。
5. 回归测试必须覆盖路径，而不只是覆盖输出。
6. 可观测性应该围绕“漂移”设计，而不只是围绕“错误”设计。

## 结语

Agent 的稳定性，最终不是来自“模型每次都想对了”，而是来自系统把它可能犯的错限制在了一个可接受范围内。

从这个角度看，四层治理的意义，不只是修掉几个 bug，而是给工具调用建立一套真正可以扩展的工程边界：

- 分流层负责高确定性任务
- 约束层负责缩小决策空间
- 反馈层负责克制纠偏
- 守卫层负责防止退化

这也是 Bee 这一轮改造最重要的收获：我们开始不再把“工具选择”当成一个 prompt 技巧问题，而是把它当成一个正式的系统设计问题。
