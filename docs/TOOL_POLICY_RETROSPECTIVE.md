# Bee 工具路由与执行稳定性改造复盘

## 引言

这一轮改造，表面上看是在修若干零散的问题：`deep_search` 超时、`cat README.md` 找不到文件、分析 GitHub 仓库时误用本地工具、问“今天有什么新闻”却返回几天前的内容、查天气时先跑到 Wikipedia、前端“思考步骤”不断堆叠重复信息，等等。但如果把这些问题放在一起看，会发现它们并不是相互独立的偶发故障，而是同一类系统性缺陷在不同场景下的反复显现。

这篇文章总结这轮问题暴露出的根因、改造过程中的关键判断，以及对后续 Agent 工程化建设最有价值的经验。核心结论很简单：工具选择不应该只依赖模型的“理解能力”，而应该被设计成一个可约束、可纠偏、可观测的运行时系统。

## 一、问题表象很多，但根因高度一致

最开始暴露的问题看起来非常分散。

第一类是超时和执行失败。例如 `deep_search` 明明在配置里写了更长的超时时间，运行时却还是被统一的 30 秒超时截断。又比如 `deep_search` 汇总阶段要求 LLM 严格吐 JSON，只要模型略微偏离格式，整个流程就会以“解析失败”结束。

第二类是路径和作用域混淆。用户问的是外部 GitHub 仓库 `paperclipai/paperclip` 的技术架构，系统却去调用 `cat README.md`、`code_read package.json`、`ls .`，最后只在本地 `workspace/` 里看到 `memory/` 和 `sessions/` 两个目录。这说明模型没有正确区分“外部仓库”和“当前工作区”。

第三类是工具职责交叉。`search` 能抓网页，`browser` 能看网页，`github_repo_inspect` 也能分析 GitHub；`cat` 能读文本，`code_read` 也能读文件；`deep_search` 似乎也能“研究”。在工具边界没有被明确定义时，模型会基于局部词面相似性做选择，而不是基于问题域、数据来源和结果质量做选择。

第四类是时效性问题。用户问“今天有什么新闻，推荐 5 条”，系统却给出 3 月 12 日的内容；问“吉隆坡明天天气”，系统先去搜索 Wikipedia，再进入 `deep_search`。这说明系统没有把“当前时间敏感的信息”视为一类特殊任务，也没有在记忆注入、工具选择和结果验证上做差异化处理。

第五类是前端交互问题。虽然不是模型能力本身的问题，但“思考步骤”不断重复“理解问题”“组织上下文”“整理到长期记忆”，会让用户觉得系统在原地打转。这类表现层冗余会放大系统实际存在的路由问题。

把这些现象抽象一下，根因主要集中在四点：

1. 工具边界不清。
2. 路由主要靠 prompt，没有运行时硬约束。
3. 工具返回结果格式不统一，模型难以判断是否已经“足够回答”。
4. 缺少统一的观测与纠偏机制，错误只会以个案形式不断复发。

## 二、不要把工具选择当成纯 Prompt 问题

很多 Agent 系统在早期都会犯一个常见错误：认为只要把工具描述写得更清楚、把系统提示词写得更长，模型就会自动学会正确选择工具。实际运行一段时间后会发现，这种方法有用，但远远不够。

原因很现实。模型并不是在做严格的“调用规划搜索”，而是在一个上下文里用语言模式匹配去猜测“哪个工具最像是能解决问题的”。一旦多个工具都能勉强覆盖同一类任务，或者上下文里又混入了记忆、历史消息、恢复提示、工具报错，工具选择的稳定性就会快速下降。

例如：

- 用户问“这个 GitHub 项目的技术架构是什么”，模型会看到 `package.json`、`README.md` 这些词，于是误用本地文件工具。
- 用户问“今天有什么新闻”，模型看到了长期记忆里的旧摘要，又看到了“新闻”这个词，于是直接把旧内容拿来回答。
- 用户问“明天天气”，模型明白这需要外部信息，但缺少天气专用工具时，它只能在 `search`、`deep_search`、`browser` 之间碰运气。

这些都不是提示词能完全解决的。因为问题不在于模型“不理解中文”，而在于系统没有把决策空间缩小到一个足够安全、足够明确的范围。

这轮改造里最重要的认知转变，就是把“工具调用”从纯语言推理问题，升级成“路由系统 + 策略系统 + 执行保护”的工程问题。

## 三、第一步：先把工具边界切清楚

稳定性的前提，是职责单一。

如果一个工具既做网页抓取、又做 GitHub 仓库分析、还顺手抓 README；另一个工具也能看 GitHub 页面；第三个工具还能做“深度搜索”，那么模型在选择时几乎不可能长期稳定。它只会越来越依赖启发式和偶然上下文。

因此我们先做了工具职责拆分。

最典型的是 GitHub 仓库分析。原来 `search` 对 GitHub URL 做了很多特殊处理，但这会让 `search` 既像“网页抓取工具”，又像“仓库分析工具”。后续我们把 GitHub repo/blob/tree 分析能力独立为 `github_repo_inspect`，并让 `search` 明确退回“通用网页抓取”。

这一步的收益非常大。因为一旦“GitHub 仓库结构分析”有了唯一主入口，模型即使偶尔选错，也可以在执行层被自动重写到正确工具，而不是在多个相似工具之间来回漂移。

同样的思路也用在天气问题上。天气属于高时效、结构明确、用户期待值很高的一类任务。继续依赖通用 `search` 只会让系统不断抓到噪音页面，因此增加了 `weather` 专用工具，通过 `wttr.in` 直接获取今天或明天的天气结果。结果是：不仅调用路径变短了，错误恢复链也显著减少。

经验是：当某类请求足够常见、结果格式足够结构化、用户容错率又足够低时，应优先设计专用工具，而不是让通用工具“兼容”它。

## 四、第二步：建立统一的 Tool Policy，而不是到处写特殊规则

仅仅拆工具还不够。因为 Planner 仍然可能选错工具，尤其在长上下文、多轮恢复、记忆注入之后。

如果每遇到一个问题就在局部补一条 if/else，系统会很快失去可维护性。因此后续做了统一的 `tool_policy` 层，把原来零散的路由逻辑升级为正式机制。

这个策略层主要承担五件事：

1. 查询分类。识别它是直接解释型请求、外部 GitHub 仓库分析、时效性请求，还是一般问题。
2. 候选工具过滤。在规划前缩小工具集合，而不是把全部工具一股脑暴露给 Planner。
3. System Hint 注入。根据查询类型追加更有针对性的运行时提示。
4. Tool Call Rewrite。Planner 虽然选错了，但执行前还能被自动改写。
5. Tool Call Guard。对明显不合理的工具调用直接拦截，而不是任其执行后再恢复。

这五件事放在一起，才真正构成“策略层”。

例如，对于“外部 GitHub 仓库技术架构分析”：

- 规划前只保留 `github_repo_inspect`、`search`、`browser`、`deep_search` 这类远程工具。
- 如果 Planner 仍然产出 `search + GitHub repo URL`，执行前自动改写成 `github_repo_inspect`。
- 如果 Planner 想调用 `ls`、`cat`、`code_read`、`shell` 这些本地工具，则直接拦截，并给出恢复提示。

对于“今天/最新/当前”的时效性问题：

- 明确打上 `TimeSensitiveCurrent` 标签。
- 强制注入当天绝对日期，而不是依赖模型隐式理解“今天”。
- 禁用长期记忆注入，避免旧摘要污染当前回答。
- 限制为新鲜数据工具，不允许本地目录探测。

这个体系的价值在于：它把一类 bug 的修复，从“某个具体 case 的补丁”，提升成“所有同类 case 的统一处理”。

## 五、第三步：让工具返回结构化结果，而不是一大段原文

很多路由问题，并不是第一次工具选错，而是工具执行完以后，模型不知道“结果够不够”。于是它会继续试第二个、第三个工具，最终走偏。

因此后续专门引入了统一的结构化输出格式。核心字段包括：

- `tool`
- `summary`
- `sufficient_to_answer`
- `data`

这样做有两个直接好处。

第一，Planner 更容易收口。比如 `github_repo_inspect` 已经返回了 `repo_summary`、`detected_stack`、`key_files_found`，系统就可以明确告诉模型：这些已经足够回答用户的问题，不要再继续调用本地工具。

第二，前端和观测层也更容易利用结果。过去工具返回的是自由文本，前端只能原样展示，恢复器也很难判断这是不是有效信息。结构化输出之后，无论是后续总结、调试、统计，还是 UI 展示，都有了稳定接口。

这里有一个工程经验：不要奢望 LLM 永远能从一大段原文中稳定提炼“我现在可以回答了”。更可靠的做法，是让工具在离数据最近的地方，就给出足够明确的“结果摘要”和“可回答信号”。

## 六、第四步：对时效性请求做单独治理

时效性问题是 Agent 产品里最容易出事故的一类请求。因为它们同时具备三个特点：

1. 用户预期明确，容错率低。
2. 答案会随日期变化，旧信息的危害很大。
3. 通用搜索很容易引入噪音页、聚合页或过期内容。

这轮实践里，最典型的坑就是“今天有什么新闻，推荐 5 条”却返回 3 月 12 日的内容。根因不是搜索失败，而是长期记忆参与了本轮规划，把旧摘要作为看似相关的信息送进了模型上下文。模型再聪明，也无法凭空知道那段旧内容不应该被引用。

因此，针对时效性问题，后续做了三项硬规则：

1. 明确识别“今天、最新、当前、明天、新闻、天气、价格、比分”等组合。
2. 禁用长期记忆注入。
3. 强制在提示中加入绝对日期。

这看似只是小改动，但实际上是把“时间”正式纳入了任务建模。也就是说，系统不再假设所有问题都能沿用同一套记忆和工具策略，而是承认有些问题天然需要“新鲜度约束”。

从工程经验看，凡是涉及新闻、天气、股票、汇率、体育、法规、领导人、CEO 等信息，都应当默认进入“高时效模式”，而不是交给普通搜索链路随缘处理。

## 七、第五步：前端表现会放大后端问题

很多团队会把“思考步骤 UI”当成纯展示层，但这轮经历说明，展示层并不只是 cosmetic。

当系统重复输出“理解问题”“组织上下文”“整理到长期记忆”，用户会自然推断：系统在空转，或者 Planner 陷入了循环。即使后端最终能回答，用户也会对稳定性失去信心。

因此我们做了两件很实用的小事：

1. 同阶段步骤合并更新，而不是重复追加。
2. 每条只展示两行，但支持“一键复制全部步骤”。

这背后的经验是：工程上必须区分“内部运行细节”和“对用户有价值的过程信息”。Agent 的中间状态可以很多，但不应该无筛选地全部暴露出来，否则会让用户看到大量低信号噪音，并误解系统质量。

前端压缩并不能替代后端修复，但它能让真正有价值的链路更可理解，也更便于排查。

## 八、第六步：可观测性不是锦上添花，而是防止回归的基础

如果没有观测，很多修复只能停留在“看起来好了”。但工具路由问题的可怕之处在于，它们非常容易在新场景里复发。

因此后续把以下指标纳入了观测：

- Planner 原始工具调用是什么。
- 是否被策略层重写。
- 是否被策略层拦截。
- 哪类查询最容易触发恢复。
- 哪对工具之间最容易出现误选。

这些数据的重要性在于，它把问题从“用户偶尔反馈的一次坏体验”，变成“我们能持续统计和优化的系统现象”。

经验是：Agent 系统里，工具路由错误一定会继续出现。真正重要的不是幻想把错误降到零，而是把它变成可分类、可量化、可复现、可回归测试的问题。

## 九、最值得沉淀的工程原则

回头看这轮改造，最值得固化成长期原则的有以下几条。

第一，工具一定要有明确所有权。一个问题域尽量只有一个主工具入口。

第二，规划前先缩小候选集，比事后恢复更重要。最好的恢复，是根本不给模型犯那类错误的机会。

第三，执行前的 rewrite 和 guard 是必要的。Planner 并不可靠，运行时必须有最后一道保护。

第四，工具输出要结构化。只返回原始文本，会把收口压力重新甩回给模型。

第五，时间敏感问题必须单独建模。不能把“今天”“明天”“最新”当成普通语义词处理。

第六，前端展示也要参与系统质量建设。冗余步骤会放大后端不稳定感。

第七，观测先行。没有统计和日志，所有修复都难以证明有效。

## 十、后续仍然值得继续推进的方向

虽然这一轮已经明显稳定，但如果从长期工程化角度看，仍有几件事值得继续做。

其一，是把更多工具纳入 metadata 驱动的治理。例如进一步细化风险级别、数据新鲜度要求、适用场景与禁用场景，让策略层不再依赖过多硬编码规则。

其二，是继续建设专用工具。新闻、汇率、股价、体育比分这类任务，本质上和天气类似，都更适合专用接口，而不是通用搜索。

其三，是补齐回归测试。尤其是“查询类型 -> 候选工具集合 -> rewrite -> guard -> 最终回答”的全链路测试，这比单个工具的单元测试更能防止退化。

其四，是让 Critic 更加克制。Critic 可以帮助纠偏，但如果它过于激进，也会逼 Planner 进行无意义的继续搜索。因此 Critic 的边界和触发条件也应该被工程化治理。

## 结语

这轮问题给出的最大启示，并不是“Prompt 还可以继续优化”，而是：Agent 的稳定性本质上来自边界、约束、结构和观测，而不是来自模型在每一次决策里的临场发挥。

换句话说，一个能稳定工作的 Agent，不是因为它“每次都想对了”，而是因为系统把它能犯的错限制在一个可接受、可修复、可持续优化的范围内。

从这个角度看，这轮改造真正完成的并不只是若干 bugfix，而是一次方向调整：我们开始把 Bee 从“依赖模型自由发挥的工具调用器”，逐步建设成“有正式路由策略、有执行保护、有结构化返回、有前端收敛、有可观测闭环的 Agent 系统”。

这比修掉某一个 bug 更重要，因为它决定了以后再遇到同类问题时，我们不再需要从零开始猜，而是可以沿着一套已经验证过的工程路径快速定位、修复并沉淀经验。
